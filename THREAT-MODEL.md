# Threat model

This is the threat model REQ-SEC-002 requires. Security overrides every other requirement (decision E.32). Review and update it at the end of every milestone, and whenever an input source or output is added.

## Assets

| Asset | Why it matters |
|---|---|
| The host device and its resources | A decoder bug must not become code execution, file access or denial of service. |
| The viewer's keys for channels (held by the browser's trusted core, never by the engine) | Possession is the viewer's identity on one channel (DEC-6471). The engine only carries their challenges and proofs and defines the bytes signed. |
| The user's trust in what is displayed | A page must not be able to fake receiver messages, security markers or link destinations. |
| The user's local network | A web-native client on a home network can be used to reach routers and other devices. |
| The user's terminal | Escape sequences in output can rewrite the screen, change titles or worse. |
| The integrity of the build and release | Dependencies and tools can be replaced by attackers. |
| The user's privacy | Requests and history reveal what the user reads. |

## Attackers

1. **Anyone able to supply input**: a file, a broadcast or recording, a web service, a pushed message or a live feed.
2. **Anyone on the network path**, especially for plain HTTP, which is allowed (decision E.32).
3. **The software supply chain**: dependencies, toolchains and build tools.

## Trust boundaries and protections

| Boundary | Attacker | Asset | Protection |
|---|---|---|---|
| Untrusted bytes into the format readers (L0) | 1 | Host | Streaming parsers with bounded memory, no panics, checked arithmetic, fuzzing (REQ-GEN-008, REQ-SEC-003, REQ-TST-040). |
| Packets into acquisition (L1, L2) | 1 | Host | Fixed-size store over caller memory, bounded work per packet (REQ-SEC-012). |
| Page content into the grid (L3) | 1 | Trust | Row 0 columns 0 to 7 cannot be written by any page route (REQ-SEC-005, E.5 (j)). |
| Sprites and the animation state over the grid (L3, L4; animation.md ANIM-6 to ANIM-8, ANIM-16; REQ-6529) | 1 | Host, trust | A sub-page holds at most 32 sprites of at most 16 frames, and at most 32 sprites and controls hold animation state, 16 cycling (`limits`); a set of sprites with a field outside its range is refused whole (`sprites::Sprites::new`), and an operation outside its range does nothing. A sprite's object is invoked by the enhancement walk under the limits of Annex A.8, counted with the page's own objects, so `MAX_WALK_STEPS` bounds the work of a grid as it did (threat 11 of page-rules.md section 12.3; the per-tick repaint budget `MAX_ANIMATION_PIXELS_PER_TICK` is the decoder's to hold). A sprite writes only inside its own width and height, columns 0 to 39 and rows 1 to 23, and sets no screen or row colour, so no sprite reaches row 0, the receiver's row 24 or a cell outside its bounding rectangle (REQ-SEC-005); the animation state is the receiver's own and no page reads it. Reviewed 18 November 2026. |
| Output to the terminal (L5) | 1 | Terminal | Allow-listed characters only; only our own fixed escape sequences; image data encoded from pixels (REQ-SEC-010, REQ-RND-029). |
| Untrusted bytes into the web user agent (L7) | 1, 2 | Host, network | Strict address parser, minimal user agent profile, strict HTTP framing, no compression, size and time limits, policy checks on every connection and redirect (REQ-WEB-014 to 016, REQ-SEC-006 to 011). |
| A web page read by discovery, and a font fetched from an address (`Input::FetchResource`) | 1, 2 | Host, trust | One `GET` on a connection of its own, redirects checked for the local network and downgrade; discovery reads only `Link` fields and `<link>` elements in the first 8,192 bytes by bounded readers, fuzzed (`discovery_header`, `discovery_element`), and checks every target before reporting it (REQ-2476); a font is taken only as a font's media type, within the core's bound, and its SHA-256 is the port's to check (REQ-123). |
| Plain HTTP connections | 2 | Trust, privacy | Unencrypted marker in the status area, no downgrade (REQ-SEC-007, REQ-SEC-008). Viewer state behaves the same on plain connections; a network observer may recognise a browser's public key there, but no secret travels (VS-115, viewer-state.md section 10.3 rows 5 and 9). |
| A page's form lines | 1 | Trust | None to protect: the TTI Form Extension is withdrawn (decision E.126), and its lines are unknown commands, ignored with a diagnostic (REQ-INP-013). A channel asks for text over the input protocol instead (area INT). |
| Links | 1 | Trust | Receiver-drawn link row, other services marked and confirmed (REQ-SEC-024, REQ-NAV-011, REQ-NAV-012). |
| A channel's log lines | 1 | A developer's console, trust | `LG` lines are refused whole unless one of three levels and 1 to 200 bytes of UTF-8 with no control or bidirectional formatting character, at most 16 per page; never drawn on a page; fuzzed (REQ-INP-026, decision E.109). Reviewed 23 October 2026. |
| The `neottx` process | 1 | Host | No `unsafe` code; the library crates have no operating-system access (REQ-SEC-016); Landlock and seccomp on Linux after inputs and outputs are open and before any of them is parsed (REQ-SEC-017); where neither the seccomp filter nor Landlock's network rules exist, `neottx` refuses unless told to continue (DEC-2351). |
| Fetcher to decoder (web mode) | 1, 2 | Host | Privilege separation (REQ-SEC-018): the fetcher process holds the network and TLS, the decoder holds the terminal and files. They speak a framed pipe protocol whose every frame is length-checked and validated by the receiver; the decoder ignores frame kinds only it may send; the frame kinds are distinct and never reuse a retired one, which the build asserts; the frames are fuzzed (`pipe_frames`). |
| Picture files into `neoteletext-picture` and `neottx-picture` | 1 | Host | File, sides and decoded size bounded before pixels are decoded; checked arithmetic on the picture's sizes; no operating-system access in the library, so a program confines it; fuzzed by `picture_convert` (REQ-2330, DEC-2325). |
| Requests the receiver makes | 1, 2 | Privacy | No `Referer` header; a minimal, fixed request profile with `Accept-Encoding: identity` and no identifying headers beyond the `User-Agent` product (REQ-WEB-031); cookies only as REQ-WEB-006 allows, never saved between runs unless the port enables it, and a response from outside the channel stores none (REQ-SEC-013, decision E.114 item 2); pre-fetching only from the service of the page being viewed (REQ-NAV-004). The owner is asked to confirm these rules (TODO-2253). |
| Cookies | 1, 2 | Privacy | None: the engine sends no `Cookie`, ignores every `Set-Cookie` and `Clear-Site-Data`, and has no SET_COOKIE record (type 8 retired); cookies and Device Bound Session Credentials were removed (DEC-6471, VS-201). |
| The return channel: keys, pointer and touch sent to a channel (decision E.125, DEC-657; area INT; push protocol 9, page-rules.md RULE-46 and RULE-49; REQ-6528) | 1 | Privacy, trust | A viewer's input reaches a channel only inside the `RULE_EVENT` of a rule of the page's own table that asked for it, and a page with no table is sent nothing (REQ-6523, RULE-50): the input session refuses a viewer's input at the top level of the stream when it writes (`SessionOf::send`) and when it reads (`read_message`, `StreamDecoder::push`), so neither a receiver nor a server built on the crate can pass one bare; the descriptor's `push.input` and `push.wheel` are withdrawn and mean nothing. Messages go only to a push WebSocket on the descriptor's own origin (`Descriptor::push_takes_messages`, finding F-90). Each message is bounded (`MAX_INPUT_MESSAGE`, 8,192 bytes) on both sides of the pipe and read by the bounded readers of `neoteletext-input`, which are fuzzed (`input_session`, `input_stream`, `rule_event`, `page_state`). `neottx view` and `neottx keyboard` evaluate the table themselves and send only what its rules report (`crates/neoteletext-cli/src/page_rules.rs`); in the browser the trusted core is the gate (RULE-52), which is the browser's to hold. Reviewed 3 November 2026; version 9 reviewed 18 November 2026. |
| A channel's records on the push connection: index, `LOG`, `LINKS`, `SUBPAGES`, `DENIED`, `REDIRECT`, viewer state's `STATE_CHALLENGE`, `STATE_END` and `STATE_KEEP_OFFER`, and the input messages with `STATE_PROOF`, `STATE_NONE` and `STATE_OFFER` | 1 | Host, trust, the viewer's keys | Each read by its own bounded reader in `neoteletext-web` (`records/`) or `neoteletext-input` (`state`), every viewer-state field of fixed length and enumerated value, refused whole when malformed, each with a fuzz target (`links_records`, `subpages`, `redirect_records`, `control_records`, `cursor_records`, `input_stream`, `channel_log`, `state_records`, `state_messages`). The agent answers no challenge itself: the port's key signs the bytes `viewer_state::signed_bytes` builds from the port's own channel identity, never from anything the server sent (VS-103, VS-203). Reviewed 3 November 2026; the viewer-state rows not yet reviewed. |
| A page's rule table: the RULES record, its decoder and its evaluator (`neoteletext-rules`; page-rules.md RULE-1, RULE-5, RULE-6, RULE-56, RULE-57, RULE-70; REQ-6526) | 1 | Host, privacy | Not a program: a table is declarations and at most 64 rules of one trigger, one condition tree and at most 16 actions, with no loop, jump or call (RULE-1). It is at most 8,184 bytes, decoded once into fixed arrays by a crate that is `no_std`, allocates nothing, has no dependency, forbids `unsafe` and denies the panic lints; a table with any field out of range, any reserved bit set, any reference to what it does not declare, a short body or bytes after its end is refused whole, the page then has no table, and nothing of it is kept or repaired. A tick is one pass in a fixed order in which nothing an action does is seen in the same tick, takes at most 16 input events from a queue of 64 and runs at most 256 actions, so the work of a tick is bounded by constants. An input event handled on arrival (`Evaluator::push_now`, RULE-96, DEC-6580) is an event of the next tick handled early: it reads that tick's one snapshot, counts against that tick's 16 events and 256 actions and against the queue of 64, and only its rules' sound operations leave before the tick, so evaluation on arrival adds no work, no state and no output a table did not have. The evaluator reads the page only through the `World` its receiver gives it and has no output but that: it cannot name another page, a file or an address. Fuzzed: `rules_decode`, `rules_evaluate`, `rules_no_unasked_send` (no report is made that no rule asked for). Reviewed 18 November 2026. |
| The answer to a state query and the fault report (`PAGE_STATE`, `RULES_FAULT`; RULE-47, RULE-48) | 1 | Privacy, host | A `PAGE_STATE` is at most 1,800 bytes, holds only the open page's own rule state (its variables, timers, the targets and values its own table names) and is written and read by one bounded codec (`neoteletext_rules::state`, fuzzed as `page_state`); a query of a page that is not open is ignored, and `neottx` answers at most one a second. A fault report carries a code and a count, nothing of the page. How often a compromised decoder may send either is the browser's trusted core's to hold (RULE-52 items 5 and 6). Reviewed 18 November 2026. |
| The animation records on the push connection: `ANIMATE`, `SPRITES`, `NAPLPS_OBJECTS`, `SHEET` and `FRAME` (animation.md ANIM-2, ANIM-6, ANIM-7, ANIM-11, ANIM-16, ANIM-17; REQ-6529) | 1 | Host, trust | Each read by its own bounded reader in `neoteletext-web` (`records/`), refused whole when a field is out of range, a reserved bit is set, a count is over its limit or bytes follow its end, and each writer checked by its reader; an operation is read by the one function a rule's action is read by (`neoteletext_rules::animate::read`). An atomic frame cannot hold a picture back for good: at most 4 pages have one open, each ends at 262,144 bytes held or after 120 ticks, and however it ends what it held is applied (`records::frame::OpenFrames`, which holds no bytes itself). A sprite sheet is at most 65,536 bytes. Fuzzed: `animate_record`, `sprites_record`, `naplps_objects_record`, `sheet_record`, `frame_records`, and `sprites_compose` from the records to the picture. Reviewed 18 November 2026. |
| A program's redirect to another channel (REQ-1688) | 1 | Trust | Shown as the one-second "Redirecting to:" notice, bounded in number of hops, and the viewer's own choice wins; a redirect from `https` to plain `http` is refused (REQ-SEC-007, DEC-2378). The security review owed by TODO-1691 is open. |
| Sound: the audio profile's packets and Opus (decision E.123, DEC-647) | 1 | Host | Bounded record store and arena, a decoder with no panics and no unchecked arithmetic, compared bit for bit with libopus, fuzzed (`audio_packets`, `audio_records`, `audio_messages`, `audio_file`, `opus_packets`); `docs/spec/design/opus-security.md`. Reviewed 26 October 2026. |
| Local sounds and what a rule reads of a sound (page-rules.md RULE-28 to RULE-33, RULE-60, RULE-62; REQ-6527) | 1 | Host, privacy | A local sound is announced by an OBJECT with tag 9 and one setup block, which the audio receiver checks as it checks every sound and hands its sink as a start, never as a stream; a view holds at most 2 (`MOST_LOCAL_SOUNDS`). Its instrument is the family's own, `no_std`, allocation-free and without `unsafe`, given MIDI channel voice messages only (`midi::rule_message`), and rendered in blocks of at most 128 samples that the mixer pulls. What a rule reads is a number: a readable patch field by its place in the family's `PARAMETERS` table (the commit gate holds appendix A of page-rules.md to the tables), a tracked value of the performance, an envelope stage and level, or a voice's peak since last asked, measured in the mixer before any volume the viewer set. That one view's levels are reported only to that view is the browser's sound helper's to hold (RULE-33; threats 7 and 8 below). Fuzzed: `local_midi`, with the bank and event readers of `audio_event_blocks`. Reviewed 18 November 2026. |
| `neottx qr` and `neottx keyboard` with the qrkeyboard relay (decision E.93) | 1, 2 | Host, the user's typing | TLS to the relay; pairing by SPAKE2 with a PIN, then end-to-end encryption with a counter that refuses replay; secret-derived bytes compared in constant time (`subtle`, DEC-640); releases passed on only for held keys. `neottx keyboard` holds the network and runs without the sandbox (DEC-618). The relay's responses have no fuzz target yet (TODO-2093). |
| `neoteletext-transport`: sockets, TLS and proxies for `neottx` and the browser (DEC-1905) | 1, 2 | Host | An application crate, never a library crate (`check-io` stays whole); reads are bounded by the callers' frame and response limits; the proxy handshake is fuzzed (`proxy`). |
| `neottx probe` (DEC-1759 lesson 20) | 1 | Host, terminal | Runs as a live input: two processes, the decoder sandboxed, every line it prints through the terminal allow-list (REQ-SEC-010). |
| The script of `neottx render --frames` and the records it applies, and the table and inputs of `neottx rules-run` (ANIM-18) | 1 | Host | Read before the sandbox closes and parsed after it, at most 4 mebibytes, each record body at most 8,184 bytes; a rule table is decoded by `neoteletext-rules`, refused whole when malformed, and evaluated for at most 36,000 ticks, the inputs giving at most 256 objects a rectangle; a line or a record body that is not understood is refused with its line number, never guessed at; a sequence is at most 36,000 ticks, and an atomic frame holds at most 262,144 bytes for at most 120 ticks. Images are written only beside the output named, with names made from the output's own name and a tick. Reviewed 18 November 2026. |
| Dependencies and tools | 3 | Build | Every library approved by the owner by name; microcontroller crates take only the dependencies `cargo xtask check-deps` permits (decision E.38, as amended); `Cargo.lock` and `fuzz/Cargo.lock` committed; the toolchain and the development tools pinned and checked by SHA-256 (`scripts/tools.sh`); `cargo-deny` and `cargo-machete` in the full gate, which cannot skip them (REQ-SEC-014). |

## The page rule table's threats

The security analysis of the page rule table is section 12 of neoteletext-common's `docs/page-rules.md`; its table of threats (section 12.3) is repeated here by number, with what in the engine answers each and what is another repository's to hold (RULE-80). The full statement of each threat and of what remains is that document's.

| # | Threat | What in the engine answers it | Held elsewhere |
|---|---|---|---|
| 1 | A table that is a program: loops, recursion, unbounded work | `neoteletext-rules`: one pass a tick in a fixed order, no cascade within a tick, at most 256 actions a tick (`MAX_ACTIONS_PER_TICK`); the worst case is constants | Nothing |
| 2 | A table built to exhaust memory or to crash the decoder | The crate allocates nothing and denies the panic lints; `decode` refuses a table whole; fuzz targets `rules_decode` and `rules_evaluate` | The decoder process's confinement (the browser) |
| 3 | A page that takes input the viewer did not mean for it | The table's interest mask (`table::Index`), by which a receiver gives only the classes of input a table asks for; a page with no table is given none | Which page is open, and the browser's own keys (RULE-51, RULE-58) |
| 4 | Input leaving for somewhere else | The input session writes a viewer's input only inside a `RULE_EVENT`, on the one session of the page's channel | The trusted core builds each report from its own copy of the event (RULE-52 items 3 and 4) |
| 5 | A decoder taken over, asking the core to send what the viewer never did | The evaluator reports an event by its sequence number, never its bytes (`Reported::Input`); fuzz target `rules_no_unasked_send` | The trusted core drops a number it never gave (RULE-52 item 3) |
| 6 | A covert channel out through values | `PAGE_STATE` is bounded and answered once a query | The budgets on valued reports and on queries (RULE-52 items 5 and 6) |
| 7 | Learning the viewer's settings or other tabs through metered values | The mixer measures a voice's peak before the master volume and the mute (`Mixer::take_peak`) | The helper reports a view's values only to that view (RULE-33) |
| 8 | A sound helper taken over through an instrument | The instruments and the mixer are `no_std`, allocation-free and forbid `unsafe`; every family's bank reader and message reader is fuzzed (`local_midi`, `audio_event_blocks`) | The trusted core accepts a report only of the length it asked for (RULE-33 item 4) |
| 9 | Sound as a nuisance or a weapon | The audio profile's limiter and gain bounds are unchanged; a local sound is an ordinary voice of the mixer | The viewer's volume and mute; ending a local sound when its page closes (RULE-60) |
| 10 | Processor exhaustion through local instruments | At most 2 local sounds a view (`MOST_LOCAL_SOUNDS`), each pulled in blocks of at most 128 samples | The overrun stop (RULE-62) |
| 11 | Processor exhaustion through animation actions | The limits of ANIM-16 in `neoteletext_core::limits`; a sprite's object is drawn under `MAX_WALK_STEPS` | The per-tick repaint budget (the decoder) |
| 12 | Timing: a table as a clock for measuring the machine | A page tick is all a table reads of time; `clock::Clock` slows page time under load and never skips a tick | Nothing |
| 13 | Fingerprinting the keyboard layout through `physical` and `char` keys | Unchanged: the KEY event carried both before | Nothing |
| 14 | A table that survives the page | An evaluator belongs to one opening of one page and is closed with it; variables are not kept | Stopping evaluation and local sounds when the page is not open (RULE-58) |
| 15 | The default table sending more than a page needs | `default_send_all` is one function, byte-exact, a wire vector; it sends what protocol 8 sent | The operator's choice for each channel (RULE-53, the server) |
| 16 | Evaluation on arrival (RULE-96) used to do more work than a tick allows, to act sooner than a page could, or to see what a tick would not | Nothing is gained by it. Work: an arrival is handled only when the viewer makes an input the trusted core passes, at most `MAX_EVENTS_PER_TICK` of them are handled for a tick whichever way they are given, each firing counts against that tick's `MAX_ACTIONS_PER_TICK` (256), and the snapshot is taken once a tick, not once an event. Reads: an arrival's conditions read the snapshot of its tick and the input state in arrival order, which the same event would read at the tick. Outputs: only `midi`, `play`, `stop` and `gain` leave early, to the page's own audio channels, which the table could already command one tick later; a report, and so anything sent to the channel, never leaves before the tick. The two ways are compared at every tick by the crate's property test and by the fuzz target `rules_evaluate`, and `rules_no_unasked_send` is run both ways | The decoder gives an event on arrival only for the open page and writes the sound operations through the trusted core as it does at a tick (the browser, RULE-96) |
